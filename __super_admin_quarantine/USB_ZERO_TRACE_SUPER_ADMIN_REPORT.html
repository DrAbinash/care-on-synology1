What is the Zero-Trace Super Admin?

The Super Admin Portal is the owner/operator control surface for Care Diagnostics ERP. It manages financially sensitive operations: doctor commissions, financial book audits, backup management, role permissions, and system health monitoring.

⚠️
The core security principle: No trace of the Super Admin system exists in the deployed server or codebase. Without a physical USB pen drive in hand, an attacker who fully compromises the server cannot access, discover, or even confirm the existence of these privileged routes.

The Three Pillars

🔑 Pillar 1 — Physical USB Key Gate

The Super Admin portal and all its API routes require a physical USB drive containing a secret key file (superadmin.key). Without the drive physically inserted into the operator's computer, the link does not appear in the ERP UI and the backend rejects every request.

📦 Pillar 2 — Dynamic Plugin Loading

All privileged API routes (/commission, /backup, /audit-logs, etc.) exist exclusively as a compiled JS bundle on the USB drive (superadmin-api.js). The server loads this bundle only when the drive is connected and unloads it 30 seconds after disconnection.

🫥 Pillar 3 — Zero Source Trace

The source files for all privileged routes were stripped to 35-byte stubs (// Reserved). No privileged logic exists anywhere in the deployed codebase. The full source is kept only on the USB drive and in an offline backup folder.

How the USB Gate Works (Step-by-Step)

Step 1 — First-Time Pairing

Operator presses Ctrl+Shift+K in the ERP. A pairing dialog opens. Operator selects the USB drive root folder using the browser's file picker. The directory handle is stored in IndexedDB (survives browser restarts). No password required for pairing — the USB drive itself is the physical proof.

Step 2 — USB Detection Loop (Frontend)

usbKey.ts runs a setInterval every 4 seconds. On each tick:

  • Retrieves the directory handle from IndexedDB
  • Requests queryPermission({ mode: 'read' }) — if denied, tries requestPermission
  • Reads superadmin.key from the directory
  • POSTs the key content to /api/super-admin/usb/verify
  • If { ok: true }: sets React state usbVerified = true
  • If drive removed: getFileHandle throws → sets usbVerified = false

Step 3 — Backend Key Validation

requireSuperAdminUsb.ts uses timing-safe comparison (crypto.timingSafeEqual) to compare the presented key against the SUPER_ADMIN_USB_KEY environment variable. This prevents timing attacks that could reveal partial key matches.

// Timing-safe comparison prevents key brute-force via timing side-channels
const expected = Buffer.from(process.env.SUPER_ADMIN_USB_KEY);
const presented = Buffer.from(keyFromHeader);
if (expected.length !== presented.length) { ... reject ... }
return crypto.timingSafeEqual(expected, presented);

Step 4 — Plugin Loading (Server Side)

Separately, plugin-loader.ts scans Windows drive letters D through Z every 30 seconds. When it finds a drive containing both superadmin.key (valid) and superadmin-api.js:

  • Validates the key file contents
  • Dynamically imports: import(usbPath + '/superadmin-api.js')
  • Gets the default export (Express Router)
  • Sets activePluginRouter to that router
  • Starts heartbeat: checks drive every 30s
  • If drive gone: sets activePluginRouter = null

Step 5 — Portal Loading (Browser)

The /super-admin-portal route serves an inline HTML page (embedded in app.ts as a string — no static files needed). This page:

  • Reads the IndexedDB paired directory handle
  • Reads superadmin-ui.js from the USB drive
  • Creates a <script> element and sets textContent to the JS bundle
  • Appends script to document.body
  • The React SPA mounts at window.SuperAdminPortal

Step 6 — Login

The portal sends POST /api/super-admin/login with:

  • X-SA-USB-Key: <key contents> header
  • Body: { pin: "..." }

Server creates a session token stored in super_admin_sessions DB table. All subsequent requests include this token.

The Plugin System

The plugin system is the core mechanism that makes zero-trace possible. It allows the server to dynamically load and unload API routes at runtime from an external source (the USB drive).

plugin-loader.ts — How It Works

// Simplified pseudocode of plugin-loader.ts

export let activePluginRouter: Router | null = null;

async function scanForPlugin() {
  // Try drive letters D: through Z:
  for (const drive of ['D','E','F',...,'Z']) {
    const keyPath = `${drive}:/superadmin.key`;
    const pluginPath = `${drive}:/superadmin-api.js`;

    if (existsSync(keyPath) && existsSync(pluginPath)) {
      const key = readFileSync(keyPath, 'utf8').trim();
      if (isValidUsbKey(key)) {
        // Dynamically load the plugin bundle
        const mod = await import(`file://${pluginPath}`);
        activePluginRouter = mod.default;
        startHeartbeat(drive); // unload after 30s if drive gone
        return;
      }
    }
  }
}

// Called by routes/index.ts for every SA request:
router.use((req, res, next) => {
  if (SUPER_ADMIN_PREFIXES.some(p => req.path.startsWith(p))) {
    if (activePluginRouter) activePluginRouter(req, res, next);
    else res.status(404).json({ error: 'Super Admin plugin is not loaded.' });
  } else next();
});

superadmin-plugin.ts — Plugin Entry Point

// This file is the plugin root — compiled into superadmin-api.js
// Lives on the USB drive, NOT in the deployed codebase

import { Router } from "express";
import { superAdminRouter } from "./routes/super-admin";
import { commissionRouter } from "./routes/commission";
// ... other route imports

const pluginRouter = Router();
pluginRouter.use("/super-admin", superAdminRouter);
pluginRouter.use("/commission", requireSuperAdmin, commissionRouter);
pluginRouter.use("/backup", requireSuperAdmin, backupRouter);
// ...

export default pluginRouter;

build-plugin.mjs — Build Script

This script performs the temporary-restore → compile → re-strip cycle:

  1. Copies full route source from backup_usb_isolation_restore_point/api-routes/ back into src/routes/
  2. Runs esbuild to bundle superadmin-plugin.ts → dist/superadmin-api.js (self-contained, no node_modules)
  3. Runs Vite build on the super-admin-portal → dist/superadmin-ui.js (React SPA with inlined CSS)
  4. Strips all route files back to // Reserved stubs
⚡
The full source code is exposed in the workspace only during the build (a few seconds). It is immediately re-stripped after compilation.

Zero-Trace Implementation

The "zero-trace" principle means: if someone inspects the deployed server, they find no sensitive Super Admin logic. Here is what exists and does not exist in the deployed codebase:

What is NOT in the deployed codebase

  • ❌ Any commission/backup/audit-logs/role-permissions business logic
  • ❌ Super Admin PIN hashing or login logic (in main bundle)
  • ❌ The React portal UI source (only a 1.96 MB blob on the USB)
  • ❌ The API plugin source (superadmin-plugin.ts)
  • ❌ The build script (build-plugin.mjs)
  • ❌ Any documentation mentioning USB, super-admin-portal, or PEN_DRIVE
  • ❌ The actual key file (superadmin.key)
  • ❌ The compiled plugin bundles (superadmin-api.js, superadmin-ui.js)

What IS in the deployed codebase (necessary infrastructure)

  • ✅ requireSuperAdmin.ts — session token validator (no business logic)
  • ✅ requireSuperAdminUsb.ts — HMAC key comparator (no key stored)
  • ✅ plugin-loader.ts — USB drive scanner (no routes, just loading)
  • ✅ Route stubs — 2-byte files: // Reserved
  • ✅ app.ts — inline portal bootstrap HTML (no static files)
  • ✅ usbKey.ts — frontend USB polling (key never stored in app)

The Route Stub Pattern

Each stripped route file contains only:

// Reserved

This exports nothing. routes/index.ts does not import these files — it routes SA paths exclusively through activePluginRouter. The stubs exist only to satisfy TypeScript module resolution if referenced elsewhere.

What an Attacker Sees

If an attacker gets full read access to the deployed server:

  • They see plugin-loader.ts scanning for USB files — but no USB is present
  • They see empty stubs — no business logic
  • They see the proxy in index.ts returning 404 — nothing to call
  • They see the portal HTML — just a "please insert USB" screen
  • They cannot reconstruct the API routes or portal UI without physical USB access

How to Rebuild the USB Files

ℹ️
This is only needed if you modify the Super Admin API routes or portal UI and need to re-generate the USB bundle files.

Prerequisites

  • Restore the quarantine folder back to the workspace (or keep it separate)
  • Ensure backup_usb_isolation_restore_point/api-routes/ contains the full route source files
  • Ensure artifacts/super-admin-portal/ contains the portal source
  • Ensure build-plugin.mjs is at artifacts/api-server/scripts/

Run the Build

# From the workspace root
cd artifacts/api-server
node scripts/build-plugin.mjs

# Output:
[build-plugin] Temporarily restoring routes from backup...
[build-plugin] Building backend plugin (esbuild)...
[build-plugin] Backend plugin built at dist/superadmin-api.js
[build-plugin] Cleaning up (restoring trace-free routes)...
[build-plugin] Building frontend plugin (Vite)...
[build-plugin] ✓ All plugins compiled successfully!

Copy to USB Drive

# Replace E: with your actual USB drive letter
copy artifacts\api-server\dist\superadmin-api.js E:\
copy artifacts\api-server\dist\superadmin-ui.js  E:\

What build-plugin.mjs Does Internally

  1. Restore: Copies all route files from backup_usb_isolation_restore_point/api-routes/ → src/routes/
  2. Backend build: esbuild superadmin-plugin.ts --bundle --platform=node --format=esm --outfile=dist/superadmin-api.js
  3. Strip: Re-writes each route file to // Reserved\n
  4. Frontend build: vite build in super-admin-portal directory
  5. Copy UI: dist/public/superadmin-ui.js → dist/superadmin-ui.js
