# 04 — Component-by-Component Reuse Analysis

*Synthesis document, written by the audit author drawing on docs 01, 02, 03, 05, 06. As-of commit: `15ed9dfc`.*

## How to read this

For each major piece of the MRI/CT Reporting Workspace, this document answers: can USG use it **unchanged**, does it need a thin **adapter**, does it need a genuine **abstraction** (the mechanism generalizes but needs new parameters/config), is it **MRI-only** by nature, or does USG already have something **USG-specific** that should be kept? Percentages are the audit author's estimate of "how much of this component's code/mechanism a USG Reporting Workspace could use as-is," grounded in the specific evidence cited in docs 01/03/05/06 — not a guess.

The short version, stated up front: **the presentation/workflow shell is ~85-95% reusable unchanged. The content (templates, findings catalogs, measurement formulas) is 0-30% reusable and must be built fresh for USG, using the same mechanisms.** This is exactly the architecture the current codebase's own design documents (`CARE_RADIOLOGY_MASTER_DESIGN_SPEC.md`, `docs/CARE_RADIOLOGY_BACKEND_V1_FREEZE.md`) already prescribe (see doc 02 Part 3), and it is exactly what R2.0 already did for the two USG studies it did build.

## Reuse table

| Component | Verdict | Reuse % | Reasoning |
|---|---|---|---|
| **Patient Header / study banner** | Reuse unchanged | ~95% | Pure presentation of `entry` (patient demographics, modality, status) from the worklist query — nothing modality-specific in the header itself. |
| **Study Header (technique/protocol banner)** | Needs adapter | ~70% | The component is generic; the *content* it displays (technique defaults) is per-study-type via the region/modality Settings split (doc 03 §13) — USG needs its own region entries (already partially exists: `usg-report-templates` catalog), not a new component. |
| **Clinical History (chip-based)** | Reuse unchanged | ~90% | `radiology_clinical_history_chips` is keyed by the same free-text `studyType` region as everything else in Quick Select — adding USG regions ("Abdomen USG," "Obstetric") is pure data entry, confirmed by doc 03 §13. The chip UI component itself needs no changes. |
| **Study Selection / Worklist hand-off** | Reuse unchanged | ~95% | `RadiologyWorklist.tsx` already carries USG-specific fields (`usgMeasurementCount`, `usgKeyImageCount`, `usgReportStatus`) and routes USG studies through the exact same "Report" button → `entry.id` → `/radiology/report/:studyId` path as MRI (doc 03 §14, doc 01 confirms `UsgMeasurementReviewPanel` is already embedded as a Workspace tab gated on `isUltrasound`). This is the single most mature piece of cross-modality integration already done. |
| **Template Engine (mechanism)** | Reuse unchanged | ~85% | The `StructuredTemplate` fetch/auto-select/fill-empty-only mechanism (doc 03 §4) is already modality-agnostic — it matches on `entry.modality` + `bodyPart` substring, with no MRI-specific logic. USG already has 13 templates in a parallel system (`usgReportTemplates.ts`) that could migrate into this same table. |
| **Template Engine (content)** | MRI-only / USG-only, needs new content | ~10% (of USG content already migrated into the *shared* mechanism) | The mechanism is shared; the actual template *text* is inherently per-study-type and not reusable across modalities. USG's 13 templates + `radiologyMasterTemplates.ts`'s 5 USG masters already exist as content — but in the wrong system(s) (see doc 05). |
| **Quick Findings (button UI + selection state)** | Reuse unchanged | ~90% | `QuickFindingsPanel`, `handleQuickToggle`, conflict-group eviction, and `applySectionContribution` (doc 03 §5) operate purely on data (`radiology_quick_findings` rows keyed by region), with zero MRI-specific code paths. |
| **Smart Findings Engine (section-flip mechanism)** | Reuse unchanged | ~90% | `lib/smartFindings.ts`'s exact-remove/dedupe-merge contribution algorithm (doc 03 §5) is pure and data-driven — it operates on whatever `findingsMap` and `anatomicalSection` values the active template/finding define. No redesign needed for USG; only new USG finding rows with `anatomicalSection` values matching USG template sections. |
| **Structured Finding Assistant** | Reuse unchanged | ~90% | `StructuredFindingDialog` + `fillStructuredTemplate()`'s `{key}`-substitution/optional-clause engine (doc 03 §6) is generic string templating with no modality assumptions. This is arguably the **best-suited existing mechanism for USG's most distinctive need** — e.g. a "Follicle Tracking" finding could ask `{leftCount}`, `{leftLargestMm}`, `{rightCount}`, `{rightLargestMm}` as structured questions, filling exactly the gynaecology gap doc 05 identifies, with zero new engine code. |
| **AI Impression** | Reuse unchanged | ~85% | The prompt-building + provider-abstraction call (doc 03 §7) takes `findings text + modality + style` as plain parameters — already modality-parameterized, no MRI-specific branching found. |
| **AI Copilot (RadiologyCopilotPanel — prior/consistency/follow-up)** | Needs adapter | ~50% | The mechanism (prior-study fetch, consistency checking) is modality-agnostic, but its intelligence sub-panels (`SpineIntelligencePanel`, `BrainIntelligencePanel`, `TumorFollowupPanel`) are literally MRI-anatomy-specific and would need USG-specific siblings (or to be excluded/no-op'd for USG studies) rather than reused as-is. |
| **CARE Copilot (orchestrated advisory panel)** | Reuse unchanged (mechanism), needs new knowledge (content) | ~70% | Per its own commit message (doc 03 §16), it's explicitly built by orchestrating the *existing* observer/validator/quality-score engines, not new per-modality logic — the orchestration pattern itself needs no changes for USG, only for the underlying engines it composes to have USG-aware content. Not deep-dived in this audit; recommended as an early follow-up read (see doc 09). |
| **Command Palette (Ctrl+K)** | Reuse unchanged | ~95% | Confirmed (doc 03 §8) to build its item list purely from whatever data is already cached for the currently-open study (findings/protocols/templates/history chips) — modality-agnostic by construction. Needs zero changes for USG. |
| **Keyboard shortcuts / command dispatcher** | Reuse unchanged | ~95% | `matchWorkspaceShortcut()` + the single `commandDispatcher` (doc 03 §8) binds generic actions (Save/Finalize/Next/Previous/Park/Open-viewer) with no modality branching. |
| **Draft Save** | Reuse unchanged | ~90% | The `save-draft` endpoint and `radiology_report_drafts` schema (doc 03 §9) already store `modality` as a plain field and have no MRI-specific columns or logic. USG's own separate draft table (`usg_report_drafts`) is the thing that needs reconciling — see the finalization note below and doc 08. |
| **Finalization (legacy path)** | Reuse unchanged | ~85% | `finalizeRadiologyReport()` (doc 03 §10) is already modality-generic — it resolves the study's billed test and posts to `patient_reports` regardless of modality. |
| **Finalization (structured D5/D7/D9 path)** | Reuse unchanged (but flag-gated off for everyone) | ~85% | Same modality-agnostic design; not yet live for *any* modality by default, so "reuse" here means USG inherits the same not-yet-enabled capability MRI has, not a special case. |
| **PCPNDT compliance lock (obstetric-specific finalize gate)** | USG-only, needs a real decision | 0% reusable from MRI (doesn't exist there) — but the *mechanism* to add a gate exists | This is USG's one genuinely unique finalize requirement (regulatory, not clinical) and is the single biggest reconciliation item flagged by R2.0 itself (doc 01, doc 02): `UsgReporting.tsx`/`UsgDopplerReporting.tsx` already have this logic, well-built, just not ported into the canonical path. |
| **Printing** | Reuse unchanged | ~90% | The legacy-HTML-first, structured-text-substitution-when-flagged renderer (doc 03 §11) takes a rendered body regardless of what produced it — no MRI-specific branching. |
| **Audit / Version History (amendment chain)** | Reuse unchanged | ~95% | DB-constraint-enforced linear amendment chain (doc 03 §12) operates on `patient_reports` rows generically; already used by any modality that goes through the canonical finalize path. |
| **Settings (Quick Select region/modality split)** | Reuse unchanged | ~95% | Doc 03 §13's region-vs-modality split is the clearest "already built for this" finding in the whole audit — USG needs new *rows*, not new *schema or UI*. |
| **Worklist integration** | Reuse unchanged | ~95% | Already proven live for USG (doc 03 §14, doc 01). |
| **DICOM integration (viewer launch, image references, pull pipeline)** | Reuse unchanged | ~90% | `studyLaunchService.ts`, `ReportImagePicker.tsx`/`ReportImagePanel.tsx`, and the `dicom_nodes`/`dicom_pull_jobs` pipeline (doc 03 §15) already have USG/Voluson-specific fields modeled at the schema level and are explicitly designed for reuse. The one gap is the **measurement extraction** side (`usgExtractor.ts`), which is inherently USG-specific (DICOM SR/GE-private-tag/OCR parsing of ultrasound-only concept codes) and has no MRI equivalent to compare against — this is legitimately USG-only, not a reuse gap. |
| **Measurement library (calculation engine)** | Needs abstraction — currently two incompatible, mostly-unwired systems | ~20% | Per doc 06's final assessment: neither `radiologyMeasurementLibrary.ts` (MRI-side, presentational only, no calculation) nor `usgMeasurementEngine.ts` (USG-side, has calculations but they're discarded and partly wrong) is a fit foundation as-is. The `structuredReport` catalog schema is the right shared shape but is unwired for both modalities today. This is the one component where "reuse" isn't really the right frame — both sides need the *same new thing built*, not one side copying the other. |

## Aggregate estimate

Weighting by rough implementation effort rather than a simple component count:

- **Workspace shell, workflow, and infrastructure (patient header, worklist hand-off, draft save, finalization, printing, audit, settings framework, command palette, keyboard shortcuts, DICOM/image handling): ~90% reusable unchanged.** This is the large majority of what a "USG Reporting Workspace" actually *is* as an application — and R2.0 already proved this by folding USG into the same page rather than building a second one.
- **Findings/template mechanisms (Quick Findings, Smart Findings, Structured Finding Assistant, Template Engine plumbing): ~85-90% reusable unchanged.** These are content-driven, not modality-driven.
- **Findings/template *content* (the actual USG templates, findings catalogs, seed packs for ~19 missing/partial study types per doc 05): 0% reusable from MRI (by definition — it's different clinical content), but should be authored using the exact same catalog format MRI content uses, not a new format.**
- **Measurement calculation: ~20% reusable, and what exists needs real repair (doc 06) before it's trustworthy, regardless of architecture.**
- **PCPNDT/regulatory compliance gate: USG-only, well-built already, needs porting/integration decision rather than fresh building.**

**Overall: for the workspace/platform layer, expect on the order of 85-90% code reuse. For the clinical content and measurement-calculation layer, expect close to a rebuild (0-30% reuse), using shared mechanisms throughout.** This matches, almost exactly, what `CARE_RADIOLOGY_MASTER_DESIGN_SPEC.md` already prescribed before this audit began (doc 02 Part 3) and what R2.0 already executed for the two USG studies it completed.
