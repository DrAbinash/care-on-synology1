# Local vision model benchmark — methodology and measured results

Date measured: 2026-10-21. Code under test: `main` at `6fd16cda`.
Harness: `artifacts/api-server/src/lib/reportComposer/localVisionModelsAb.live.test.ts`.
This document records what was measured and what was **not**. It is not a
recommendation to change the clinic's configured model — see "What would change the
conclusion" at the end.

## Why this exists

CARE can point its selected-image drafting leg at any local Ollama vision model, and
four are installed across the clinic's two machines. Choosing between them by name is
guesswork, and choosing by pushing a patient's study through a model nobody scored is
not acceptable. So every candidate is driven through the **shipped** path with identical
input and scored.

## What actually runs

Nothing is mocked. Each row of the table is one real request through:

`buildCareSystemPrompt` (the shipped persona) → `buildUserPrompt` (the shipped prompt
builder) → `planComposerVisionContext` (the shipped context sizer) →
`OllamaComposerAdapter.compose` (the shipped transport) → `parseComposerDraftJson` (the
shipped output contract).

The transport is called with `localOnly: true`, one image, `temperature 0.1` and a
180 s deadline. CARE never pulls weights: a model absent from `/api/tags` is reported as
skipped, and no code path in the harness asks Ollama for `/api/pull`.

## Cases, and what each one can prove

Three synthetic examinations, each a drawn schematic carrying printed labels, plus typed
observations that deliberately do **not** contain everything the drawing shows.

| case id | typed levels | typed measurement | truth side | finding present only in the pixels |
| --- | --- | --- | --- | --- |
| `lumbar-sagittal` | L2-L3, L3-L4, L4-L5 | none | left | L5-S1 |
| `brain-axial-right` | none | none | right | extra-axial |
| `knee-typed-measurement` | none | 14 mm | right | enthesophyte |

No real patient data is involved: the "images" are vector drawings generated by the
harness, and the clinical text is written for this file.

Repeated runs: 3 per case per model, so 9 runs per model per endpoint.

## How each column is computed — and the denominator trap

A preservation check is an absence test, and an absence test passes on an empty string.
Scored naively, a model that timed out nine times out of nine "kept" every measurement.
An earlier revision of this table did exactly that, and reported `meas kept 8/9` for a
model that produced two usable drafts. Every starred column is therefore scored only over
**runs that could have failed it**: usable drafts, in cases that declare the fact. `n/a`
means nothing was scoreable — it is never a pass. A unit test in the harness
(`a preservation column is never credited to a run or a case that could not fail it`)
holds that rule; mutating the filter back to "count everything" fails it.

| column | rule |
| --- | --- |
| usable | transport `ok` and a draft that parsed |
| structured | `parseComposerDraftJson` returned a draft with non-empty Findings |
| levels kept\* | all typed level tokens appear in the draft — over usable runs of cases with typed levels |
| meas kept\* / meas lost\* | the typed measurement string appears verbatim / a drawing number appears while the typed one does not |
| names side\* / SIDE WRONG\* | the true side word appears / the opposite side appears and the true one does not |
| grounded | a finding that exists **only** in the drawing reached the draft |
| invented | any `mm` figure present in neither the typed observations nor the drawing's printed labels |
| ms | wall clock per request, mean/median/min/max over all runs including failures |
| vram GB | Ollama's own `size_vram` from `/api/ps` for the loaded model |

`grounded` is a pixel-conditioning signal, not a correctness signal: mentioning L5-S1
proves the model read the drawing, and CARE's own validator then blocks that level as
unobserved. Read it as "did the pixels arrive", never as "was the finding right".

## What this does not measure

1. **Diagnostic accuracy.** No number here says a model reads a spine well. The images
   are drawings with printed labels; they prove pixels arrived, not that findings are
   correct.
2. **Omitted abnormalities** and **unsupported findings** beyond what the schematic
   encodes. A drawn label cannot represent the clinical consequences of a missed lesion.
3. **Laterality in real anatomy.** `SIDE WRONG` was 0 for every model on every run — a
   necessary result, not a reassuring one, on three cases whose side words are typed into
   the prompt.
4. **Behaviour under concurrency, all day, at the clinic** — one request at a time here.
5. Anything about cloud providers. No request in this benchmark left the building: the
   transport ran `localOnly: true` and cloud image egress stays disabled.

## Conclusions the measurement supports

- Nothing here justifies changing the production vision default today, and it has not
  been changed.
- The one finding that is hard enough to act on is negative: **`qwen3-vl:8b` produced no
  usable draft in 9 of 9 attempts on the clinic's own machine.** Whatever model is
  configured, a path that answers empty must not be recorded as a success — see the
  separate fail-closed work on `ai_reporting_audit_logs.success`.
- On the clinic AI PC the choice is between `gemma3:12b` (names the side every time,
  7.71 GB, ~28 s median) and `medgemma1.5:4b` (four-times faster, 3.46 GB, named the side
  in 4 of 9). A laterality miss is the clinically expensive failure, so a speed-based
  switch to MedGemma is not supported by this table.
- `gemma4:latest` is a real candidate but was measured on the wrong machine. It needs the
  same nine runs on the clinic AI PC before it can sit in the same table at all.

## What would change the conclusion

A radiologist scoring de-identified clinic studies on each candidate — modality coverage
that actually exists at this centre (plain films, CT, ultrasound, MRI), several readers per
study, and an explicit count of findings the model invented that no image or observation
supported. Ultrasound matters: MedGemma 1.5 covers CT, MRI, chest radiograph and
whole-slide histopathology, and **not** ultrasound, which is a large share of this clinic's
work.

## How to reproduce

```
RUN_LIVE_OLLAMA=1 RUN_VISION_BENCH=1 RUN_VISION_BENCH_REPEATS=3 \
LIVE_OLLAMA_URL=http://192.168.1.250:11434 \
LIVE_OLLAMA_MODELS=gemma3:12b,medgemma1.5:4b,qwen3-vl:8b,gemma4:latest \
vitest run artifacts/api-server/src/lib/reportComposer/localVisionModelsAb.live.test.ts
```

The run takes about 16 minutes on the clinic AI PC and 39 minutes on the development
machine. It writes `tmp/vision-benchmark.json` with every per-run row, and prints the
table to stdout. Both are read-only with respect to the clinic: no database row is
written and no study is touched.
